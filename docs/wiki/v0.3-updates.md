# grounded-mcp v0.3 — supersession, and a scorecard that reports by slice

v0.3 adds one guardrail and changes how all of them are reported. Both came from a reader.

## Where it came from

A comment on the v0.1 write-up asked two things. Report retrieval, correct abstention and false abstention by query slice rather than as aggregates, with each slice's case count next to its pass/fail. And put superseded versions in the regression set, because a suite can pass retrieval while still answering from stale evidence. Two of the three regression cases the comment named (permission-denied, unsupported questions) were already families in the suite. Superseded evidence was not, and the server had no concept of it at all.

## The measurement that decided the design

Four stale notes went into the demo vault beside their successors: last year's expenses policy, an old deploy runbook, an archived product datasheet, last year's salary bands. Same titles, same tags, old numbers. Then the v0.2 server was asked twelve questions those notes answer.

The stale copy tied its successor on BM25 score to two decimal places in 7 of 12 queries and tied on coverage in 11 of 12. It ranked first in 8 of 12 and appeared in the cited top five in 12 of 12. Where the scores tied, the stale note won every time: FTS5 returns tied rows in insertion order, notes are inserted in sorted path order, and `-2025.md` sorts before `.md`. Which version of a policy an agent would have quoted was decided by the ASCII code of a hyphen.

Both abstention gates passed the stale note in 12 of 12. That is the finding. A stale note IS relevant to the question. It is just no longer true. Score cannot see that, coverage cannot see that, and hybrid semantic retrieval would see it even less, because the two versions mean the same thing. No ranking rule separates "relevant" from "current", so v0.3 does not try to rank stale notes down. It never indexes them.

## What the old scorecard said

The v0.2 gate did go red, and it named the wrong cause: `retrieval.hit_at_1 regressed: 1.00 -> 0.82`. A ranking complaint. recall@5 stayed at 1.00 because the current note was still in the top five, and abstention stayed at 1.00 because the server was confident. It only caught anything because the golden set happened to list only the current path as acceptable. "No answer" and "no access" each had a family. "No longer true" had nowhere to show up, so it showed up as something else.

## Changes

### Supersession (server)

- Frontmatter key `superseded_by: <vault-relative path>` marks a note as stale. Only a non-empty string counts; `true` or a list is ignored, because a stale note must say what replaced it.
- Stale notes are excluded from the per-profile index at build time, the same mechanism as entitlements. They are never scored, ranked, snippeted or cited, at any threshold.
- `read_note` still returns a stale note by path, with `superseded: true`, `superseded_by` and a warning, so history is reachable on purpose and never by accident. Entitlements still apply first: a stale note in a denied zone is as invisible as a current one.
- `browse` lists current notes only; `include_superseded=true` adds stale ones, each with its successor path. Stale notes are not backlink sources.
- Server instructions tell the agent what `superseded: true` means and to read the successor instead.

### Slice-aware scorecard (evals)

- Every golden case belongs to one slice, named for the failure it can expose: `answerable`, `unsupported`, `superseded`, `denied`, `secret`. The scorecard prints one row per slice with n, pass, fail and the slice's own metrics.
- False abstention is its own count. An answerable query that abstains is `FALSE-ABSTAIN`, not folded into a miss; the retrieval metrics are unchanged but the failure line says which of the two things went wrong.
- New `superseded` family, hard zero: the stale path must not surface even unthresholded, the current path must still be found, and a direct read of the stale path must return it with the right successor pointer. Sixteen cases: twelve queries and four reads, across staff and exec.
- `denied` gains a stale-and-denied direct read, so the two mechanisms are tested together.
- Baseline schema 2 stores per-slice counts and metrics. The gate fails on any hard-zero violation, and on any slice whose fail count or metric regresses against the baseline. A pre-v0.3 baseline is detected and refused with a message rather than silently compared.

### The numbers

Before (v0.3 runner, supersession disabled): superseded 0/16, stale-cited 12, history-readable 0/4; answerable hit@1 0.79. After: superseded 16/16, everything else 24/24, 10/10, 24/24, 6/6, hit@1 1.00. The sabotage demo (thresholds to zero) still fails, now with the slice named: `unsupported.fail regressed: 0 -> 6 (n=10)`. The superseded slice stays green under sabotage because exclusion does not depend on thresholds.

Which slice proved hardest, to answer the reader directly: superseded, and not by a margin. It was not harder on a working mechanism. It had no mechanism, and the scorecard had no row for it.

### Housekeeping

- Version 0.3.0. 33 tests (7 new in `tests/test_supersession.py`). CI step renamed to list the five slices.
- README: fourth question ("is it still true?"), the frontmatter convention, the measured finding, a new honest boundary (supersession is declared, not detected), roadmap moved: hybrid semantic retrieval is now v0.4 and must publish its eval delta per slice.
- The demo gif still shows the v0.2 scorecard layout; it will be re-recorded.

## Still deliberately out (v0.4 candidates)

Hybrid semantic retrieval, with its eval delta published per slice against this baseline. Automatic supersession detection (two notes that look like versions of each other) is out on purpose: the server trusts what the vault declares and the eval slice exists so you can measure how many unmarked stale notes you have, not so the server can guess.
