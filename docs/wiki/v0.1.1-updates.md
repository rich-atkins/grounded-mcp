# grounded-mcp v0.1.1 — the worker-thread fix (found by a sibling's integration test)

One fix, worth its own page because of how it was found.

## The bug

Every DB-touching tool call failed over real MCP transport. The MCP SDK executes synchronous tool functions on worker threads; the server's SQLite index was created on the main thread, and sqlite3's same-thread default refused the crossing. `search`, `read_note`, `backlinks` and `browse` all returned an error instead of content the moment a real MCP client called them.

## Why v0.1 shipped with it

The eval suite is thorough about WHAT the server returns, and it runs in-process: single thread, no transport. The server-path smoke test listed the tools but never called one. So the suite was structurally blind to a transport-level failure: everything it measured was correct, and the thing it could not see was broken. A reminder that an eval suite's coverage claims are bounded by the path it exercises, not the assertions it makes.

## How it was found

The first integration test of [grounded-harness](https://github.com/rich-atkins/grounded-harness)'s MCP bridge — an agent harness consuming this server as a toolbox — called `search` over real stdio transport and hit the failure within seconds. The fix (a shared connection with `check_same_thread=False` behind a lock) landed the same hour, with a cross-thread regression test pinning it.

## Changes

- SQLite index usable from MCP worker threads (`check_same_thread=False` + lock serialising access).
- Cross-thread regression test: `search` executed from a worker thread must succeed.
- No metric, tool contract, or eval change; the full suite and eval gate pass unchanged.

If you installed v0.1 and the tools errored in Claude Desktop / Claude Code while the evals passed locally: this was why. Upgrade.
